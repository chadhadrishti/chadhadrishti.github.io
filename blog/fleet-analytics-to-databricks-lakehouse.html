Data platform migration

Cutting fleet analytics costs by collapsing the stack, not trimming it

How replacing a four-service Azure reporting stack with a Databricks Lakehouse cut projected analytics infrastructure spend by roughly 30% — and set the platform up for both batch and streaming from day one.

Aug 2026 · 7 min read · Drishti Chadha

A fleet management and leasing company I worked with — tens of thousands of vehicles under management, reporting across fleet operations, leasing, telematics, and finance — came to us with a familiar complaint: their Azure reporting bill kept climbing, refreshes were slow, and every new report request meant touching four different services just to get a number onto a page. The instinct in situations like this is to go optimize the expensive piece. We looked at the stack instead, and the expensive piece turned out to be the wiring between services, not any one service itself.

The stack that got expensive one service at a time

Their existing architecture was a textbook multi-hop pipeline: Azure Data Factory moved data in batch from SQL-based operational systems and Salesforce into an Azure SQL data mart, Azure Analysis Services built tabular models on top of that mart, and Power BI — running on Premium capacity to handle the load — sat on top of Analysis Services. Every layer was defensible in isolation. Together, they meant every report refresh paid the processing cost of a SQL mart and a tabular model and a Premium BI tier, and every schema change had to be propagated through three services in sequence before a dashboard updated.

Current vs. proposed architecture, redrawn from the migration plan — ingestion, medallion layers, serving, and governance

Nobody had over-engineered this on purpose — it had accreted service by service, each addition solving a real problem at the time. But it meant the SQL mart and the tabular model were both doing the same job of "get data into a shape Power BI can query fast," just at different layers, and both were on the invoice.

The fix: fewer layers, not faster layers

We rebuilt the platform on a Databricks Lakehouse using a standard Bronze/Silver/Gold medallion structure, and the deliberate design choice was to remove the intermediate hops entirely rather than optimize them:

  • Bronze — source-aligned raw data landing directly from the SQL-based operational systems, Salesforce, Cosmos DB, and flat-file sources, with historical and incremental loads, schema evolution, and reprocessing built in.
  • Silver — the legacy stored procedures and views that used to live in the SQL mart, converted into Databricks-native transformation logic, with the same cleansing and deduplication rules preserved.
  • Gold — curated, business-ready metric views mapped directly to the KPIs the existing Power BI models already reported on, so the numbers stakeholders trusted didn't shift under them.

Power BI then connects straight to a Databricks SQL Warehouse as its serving layer — no separate tabular-model service in between. Azure Analysis Services and the Azure SQL analytical mart come out of the architecture entirely, not because either was badly built, but because a governed Lakehouse with Unity Catalog access control can do both jobs — storage and semantic serving — without a service boundary in the middle charging for the handoff.

Built for streaming, not just this migration

The other reason the old architecture couldn't just be tuned in place: it was batch-only, and part of the source landscape — a Cosmos DB-backed transaction service — needed a path to near-real-time ingestion that Azure Data Factory's batch windows weren't built for. Structured streaming and Auto Loader on Databricks handle both needs on the same platform, so the transaction feed can move to streaming ingestion later without a second migration. That's the part of "collapse the stack" that's easy to miss in a cost conversation: the cheaper architecture also turned out to be the more capable one, because a Lakehouse doesn't force a choice between batch and streaming the way a SQL-mart-plus-tabular-model stack does.

The expensive part of a legacy analytics stack usually isn't a single slow service — it's the number of times data has to change shape and change hands before it reaches a dashboard. Every hop is a cost line and a failure point.

What it took to get there

This wasn't a lift-and-shift. Migrating meant re-mapping four Analysis Services models — including two multi-gigabyte ones — onto Gold-layer datasets, converting the stored-procedure and view logic that encoded years of business rules, and re-pointing Power BI reports to a new connection without stakeholders noticing a difference in the numbers on refresh day. We ran it as a phased program — environment and governance setup, then Bronze ingestion by source, then Silver conversion, then Gold and Power BI cutover, then a GenAI-powered natural-language layer on top for ad hoc questions — with validation gates between each layer so a bad conversion never made it downstream.

What it delivered

20–30%
reduction in SQL & analytics serving cost
~$60K/yr

The savings weren't the result of squeezing a single expensive service — they came from removing two of them and letting Databricks do the storage, transformation, and semantic serving in one governed platform instead of three disconnected ones. That's usually the bigger lever in a cost-transformation program: not "make the expensive thing cheaper," but "ask why there are three expensive things doing overlapping jobs in the first place."
