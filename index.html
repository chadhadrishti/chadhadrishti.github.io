Problem

Service level, demand, warehouse, and inventory data lived in SAP, BlueYonder, and manual spreadsheets with no shared model — every report was a reconciliation exercise.

What I shipped

SPEC-02 · FleetCare
Fleet management · AustraliaCost & speed

Cutting Australia's largest independent fleet manager over to a lighter, cheaper Lakehouse.

Fleetcare · 42,000+ vehicles · 80+ employees

Fleetcare's reporting stack was three paid Azure services deep before a number ever reached Power BI. I designed the architecture to cut that to one.

Expand specCollapse spec
Problem

Fleetcare's current platform routed everything through Azure Data Factory into an Azure SQL data mart, then into Azure Analysis Services for semantic modeling, then finally into Power BI Premium — three paid services doing what one governed warehouse could do, on batch-only refreshes with rising Azure spend.

What I shipped

Architected the future-state Databricks Lakehouse: direct ingestion from Salesforce, SQL Server, Cosmos DB, and ADLS Gen2 into Bronze, cleansed through Silver, curated into Gold metric views — with a single Databricks SQL Warehouse replacing Azure Analysis Services and the Azure SQL analytical layer entirely as the serving layer for Power BI.

Removing Azure Analysis Services and the Azure SQL analytical layer

Impact

Targeting a 20–30% reduction in SQL and analytics serving cost, full infrastructure consolidation (Azure Analysis Services and the Azure SQL analytical layer removed), and roughly $60,000/year in Azure infrastructure savings established during the POC — on a ~7-month delivery timeline.

SPEC-04 · Lakehouse delivery playbook
Repeatable pattern6 accounts

The same repeatable way of taking any account from "what does the business need" to a governed Lakehouse.

Scripbox · Snabbit · IBS Software · Urbint · Third Wave Coffee · Fleetcare

Every account starts the same way: understand the current stack and its actual pain, then design the smallest Databricks architecture that removes it — never a template migration.

Expand specCollapse spec
Problem

Each account arrived with a genuinely different legacy stack and a different constraint: Redshift + Meltano at Scripbox, Superset + AWS RDS at Snabbit, Aurora + Redshift + Kafka at IBS Software, Redshift + Airflow at Urbint, Azure SQL + Synapse at Third Wave Coffee, Azure Analysis Services at Fleetcare. A copy-paste migration plan would have been wrong for at least four of the six.

What I shipped
  • Discovery first — map current sources, data volumes, and the one real bottleneck (cost, latency, or governance) before proposing any architecture.
  • Right-sized design — real-time streaming where the business needed sub-10-minute latency (IBS Software's Kafka + CDC pipelines); incremental sync where cost was the issue (Snabbit, Fleetcare); straightforward batch consolidation where the win was just escaping a fragmented BI stack (Scripbox, Third Wave Coffee, Urbint).
  • Same governance floor everywhere — every design lands on Unity Catalog and a Databricks SQL serving layer, regardless of how the ingestion side differs.
The pattern, every time

Same skeleton, re-tuned per account for latency, cost, or governance

Impact

Six accounts, six different starting stacks, one repeatable architecture pattern — each landing on Unity Catalog governance and a Databricks SQL serving layer, without forcing a one-size-fits-all migration onto any of them.
